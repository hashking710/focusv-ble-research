Steps the target through each waypoint in order, interpolated linearly between them, purely on a timer — add waypoints for anything beyond a straight ramp (a fast rise then a coast, a second bump, etc). Closed-loop mode uses the same schedule but won't advance past a step until 0x99's live measured temperature is within ~15° of the last commanded target — the device has no BLE command for true continuous PID tracking, so this just paces the existing step commands by reality instead of the clock. The curve below shows the commanded line (dashed green, waypoints marked) and real measured temperature (solid orange). Each step's write carries a short session duration as a fail-safe — if this app crashes or disconnects mid-ramp, the device stops heating on its own shortly after.

Mode
Waypoints
Set the last waypoint's hold to 0 — that's what tells the device to stop advancing (the firmware treats a 0-second hold the same as a never-saved slot: end of ramp here). Values are not clamped to the normal preset range the way Quick Set is — a waypoint here is data being stored on the device, not a temperature being applied immediately. The device's own session timer has a documented ceiling (240s flower / 120s concentrate normally); whether a longer ramp keeps running past that hasn't been confirmed on real hardware yet, so keep ramps short until it has.
"Save to device" writes all 5 flash slots for the selected mode (unused trailing slots as 0°/0s, which the firmware treats the same as a never-saved slot — inert either way). "Start" arms the ramp by sending a normal start command carrying a fixed sentinel temperature (150°F) that the patched firmware recognizes in place of a real target — from there it runs the saved waypoints on its own. "Stop" is the same Cancel command used everywhere else in this app; the firmware's own session-end handling resets the ramp's progress. The device has no read-back opcode for these waypoints — Save just remembers, locally in this browser, what was last sent; it can't confirm what's actually on the device.

Byte roles are now confirmed directly from the real app's own settings-save call site: byte 2 is Order (1=Primary, 2=Secondary, 3=Primary&Secondary, 4=Secondary&Primary), bytes 3 and 4 are both the cycle duration in seconds — the real app's UI always writes the identical value to both together, never independently. A live test that sent them mismatched left the official app's own Screen Savers settings screen unreachable until the device was reset, so byte 3/4 are now locked together here and can't be sent apart.
Order is 1-4 (see above); Seconds is written identically to both byte 3 and byte 4, matching the real app exactly — there is no control here to desync them. A status refresh (below) shows what the device reports back.
Picks an image, center-crops it square, resizes to 240×240, converts to 16-bit RGB565, then streams it in 16-byte blocks over 0x74 — the same block-write opcode firmware updates use, distinguished (as far as traced) by the fixed sub-type byte in the 0x72 session-start header. Erase sends 0x83 for the selected slot. See ble-protocol-notes.md for the full pipeline. Factory reset
Sends 0xAE 0x04 0xAE 0xAE — confirmed via the real app's source (line ~282684) as the actual device-side factory reset trigger. This resets saved presets, LED settings, and (very likely) screensaver slots. Note: the real app also resets settings server-side (Firestore) before sending this BLE command — this button only does the on-device half, so it may not clear any app-side cached state.
